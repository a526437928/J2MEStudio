# 0.4.4：中文菜单靠右文字裁切

2026-11-06 用户提供实体 iPhone 截图：游戏底部菜单“选择”可见，右侧“退出”部分超出画面；用户确认此现象在 0.4.3 之前已存在，《诛仙伏魔录》和另一款游戏均可见。第二款游戏名称尚未提供。

## 源码根因

`Font.stringWidth(String)` 原来固定返回 `str.length() * 8`。实际文字由 CoreText 按字体、字号及中英文字形绘制，两者不一致。游戏常用 `canvasWidth - font.stringWidth("退出")` 计算右侧菜单位置，低估宽度会把文字放得过于靠右。`charWidth`、`charsWidth`、`substringWidth` 也沿用同一估算，影响不限于一个游戏。

[MIDP Font 规范](https://docs.oracle.com/javame/config/cldc/ref-impl/midp2.0/jsr118/javax/microedition/lcdui/Font.html)要求返回所选字体的实际 advance；[Graphics 规范](https://docs.oracle.com/javame/config/cldc/ref-impl/midp2.0/jsr118/javax/microedition/lcdui/Graphics.html)规定文字锚点与 Font 的宽度、高度及基线计算应一致。[CoreText typographic bounds](https://developer.apple.com/documentation/coretext/ctlinegettypographicbounds(_:_:_:_:))提供与绘制文字相同的排版度量。

## 实现

- Java `Font` 的公共字宽、行高与基线通过独立原生度量入口查询；在尚未设置 Graphics 字体时也能正确测量，不创建额外位图或借用可能失效的游戏绘图上下文。
- 原生测量与绘制共享同一字体选择和 CoreText 排版路径，保留原有字体家族及 10/14/18 的字号映射。右对齐/居中使用与 Java API 一致的整数宽度；BOTTOM/BASELINE 使用相同行高和基线，修正锚点不一致。
- Java 最多缓存 72 个标准字体组合，每个字体缓存 16 条、每条最多 128 个字符的宽度；原生最多缓存 36 个不可变字体，使用互斥保护。避免每帧重复创建字体或长期保留任意长文本。没有据此宣称已实测降温。
- 游戏 JAR、存档目录、帧率、虚拟按键及 miniJVM 解释器不改写，3D 和音频原功能保留。

## 验证方法与当前状态

自编诊断增加实际像素检查：12 种字体/字号/样式组合，比较 `Font` 与绘图上下文的度量、字符及子串宽度、手算靠右位置、RIGHT/HCENTER/BASELINE/BOTTOM 锚点和跨上下文稳定性。将旧的“每字 8 像素”公式用于反例，必须在实际渲染中检测出裁切，不能固定输出通过。诊断底部另绘“选择 / 退出”，右侧故意使用游戏常见的手工字宽定位方式。

Windows 已实际编译 439 个 Java API 源文件、原测试 MIDlet 和两个自编诊断源文件，8 项 Python、宿主 RMS/生命周期/输入、源码和脚本语法检查通过。CoreText 像素及新 JNI 路径需要 macOS/iOS 环境，接下来执行完整云构建与真实 miniJVM 回归，不将本地 Java 编译当作 iOS 成功。

App 与内置新诊断均标为 0.4.4，App build 为 8。本版的云构建、IPA 校验和两款用户游戏的最终真机效果将在实际完成后分别记录。
