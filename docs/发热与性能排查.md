# 0.4.3：发热与刷新开销排查

用户在 iPhone 17 Pro / iOS 27.0 运行《诛仙伏魔录》一段时间后反馈明显发热，确认当时没有充电。没有设备性能日志、实测温度或功耗数据，目前不能认定具体热源，也不能据游戏年代推断解释器的实际负载。

## 源码证据与改动

- 0.4.2 每次 Java 刷新都创建 CGImage，并向主队列提交一个显示闭包。界面处理不过来时，没有待显示帧数量限制。0.4.3 增加 `LatestFrameBuffer`，只持有最新一帧，共享一次唤醒；主线程通过 CADisplayLink 提交最新画面。被覆盖的旧帧及时释放；无新画面时暂停 display link。
- 进入后台或游戏画面离开时暂停显示，退出时销毁 display link；恢复后接收新的游戏帧。按键队列、游戏存档格式和 JVM 核心保持原实现。该机制不保证停止忽略 pauseApp 的游戏自身运算线程。
- Java Display 事件循环原本每轮连续调用四次 `Thread.sleep(4)`，其间不轮询输入。改为一次 `Thread.sleep(16)`，保留约 16 毫秒的事件轮询周期，减少额外休眠调用。不能把休眠调用减少比例说成整机功耗改善比例。
- 游戏库的背景动画在进入游戏、离开列表或失去前台时停止，返回列表再恢复，避免无必要的装饰动画。
- 每 10 秒及暂停/退出时记录 App 进程 CPU 时间、系统 thermalState、帧接收/替换/提交次数，最多保留最近 30 次采样。日志为游戏目录下 `last-performance.json`，可通过现有“导出运行日志”导出。热状态是系统分级，不是摄氏温度；CPU 数值以一个核心满负载为 100%，多线程时可以超过 100%。

原 miniJVM 在 iOS 路径禁用 JIT，仍以解释器运行。未为降低功耗任意替换 JVM、调整 GC、删除 3D/音频或改变存档。现有游戏的帧率设置也不被强制改写。

Apple 建议减少不必要的绘制与动画，并观察系统热状态：[绘制效率](https://developer.apple.com/documentation/xcode/improving-your-app-s-rendering-efficiency)、[电源与热状态通知](https://developer.apple.com/documentation/xcode/responding-to-power-notifications)。这支持本轮检查方向，不能代替此 App 的真机效果验证。

## 当前包即可做的对比

先在游戏里保存并退出。游戏库长按《诛仙伏魔录》→“帧率上限”→30 FPS，再重新启动。当前默认上限为 60；用户已设定的值优先。比较同样场景、亮度和游玩时长。如果动作或游戏速度明显变慢，恢复原值。降低帧率的实际效果需手机反馈，不能承诺固定降温幅度。

## 验证状态

新增帧队列并发、最新帧选择、对象释放、暂停与恢复检查；模拟器增加一次 1,000 帧突发输入，验证只保留一帧且旧帧被合并。保留中文、组合按键、斜向、RMS、崩溃及另一游戏存档保护回归，并核对真实 UIKit 显示和性能记录。

本地 Java、Python 与源码检查完成后，继续执行实际 macOS 云构建；最终结果按实际执行补充。本版本的真机发热改善尚未验证。CI 的模拟器 CPU 数值受宿主环境影响，不作为 iPhone 性能或温度数据。
